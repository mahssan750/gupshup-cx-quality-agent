PURPOSE
-------
This document explains the whole application from A to Z. It covers the program
structure, trust boundaries, user interactions, processing paths, stored data,
failure paths, recovery paths, and the supervisor-controlled learning loop.

The central product rule is:

  An employee is non-compliant only when an approved company rule applies,
  the customer messages establish the relevant context, and the employee
  messages show a direct violation of that rule.

Generic tone, empathy, clarity, resolution, or customer-satisfaction scores do
not create violations in this engine.

D. DEFENSE AND ADMIN LOGIN
==========================

Public before login:

  GET /                         React shell only
  GET /app-assets/*             Compiled JS/CSS needed by login screen
  GET /api/v1/auth/status       Authentication state only
  POST /api/v1/auth/login       Credential verification

Protected after login:

  - Every other /api/ route
  - React data and mutation calls
  - Legacy pages and form actions
  - Run creation, stop, resume, and result access
  - Evidence review and Knowledge mutation

Login sequence:

  Browser              Flask auth gate             Private .env
     |                        |                          |
     | GET /                  |                          |
     |<-- React shell --------|                          |
     | GET auth/status        |                          |
     |<-- authenticated=false |                          |
     | POST login credentials |                          |
     |----------------------->| compare constant-time   |
     |                        |------------------------->|
     |                        |<-- expected values ------|
     |<-- signed session -----|                          |
     | GET overview + cookie  |                          |
     |----------------------->|                          |
     |<-- protected data -----|                          |

Session controls:

  - Role must be admin.
  - Session lifetime defaults to eight hours.
  - Cookie is HTTP-only and SameSite Strict.
  - Secure-cookie mode can be enabled for an HTTPS proxy.
  - The signing secret comes from CXQUALITY_SESSION_SECRET or is generated
    in local/.session-secret, outside Git.
  - Logout clears authenticated session state and replaces the signed cookie.
  - Five failed attempts from one local address cause a one-minute lock.

Security response paths:

  Anonymous API call ---------> 401 JSON
  Anonymous legacy page ------> redirect to React login
  Wrong username/password ----> 401, no session
  Sixth attempt during lock --> 429 + Retry-After
  Expired session ------------> React receives 401 and returns to login
  Logout ---------------------> next protected API call returns 401

Browser headers:

  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Referrer-Policy: no-referrer
  Content-Security-Policy: self-hosted scripts/connections, no framing
  Cache-Control: no-store for API responses

H. HIGH-LEVEL RUN LIFECYCLE
===========================

  [ZIP folder submitted]
           |
           v
  validate folder + count *.zip + reject active duplicate
           |
           v
        QUEUED
           |
           v
        RUNNING
           |
           +--> inspect ZIPs and build session/thread map
           |
           +--> extract each primary chat
           |
           +--> eligibility gate
           |
           +--> deterministic metrics
           |
           +--> Knowledge retrieval
           |
           +--> company-supervisor-v1 evaluation
           |
           +--> persist result, spend, and checkpoint
           |
           v
  sync recurring clarification themes into Knowledge candidates
           |
           v
  Knowledge agent analyzes pending candidates
           |
           v
        COMPLETED

Alternate terminal/non-terminal paths:

  RUNNING --> BLOCKED          user stop, missing folder, recoverable issue
  RUNNING --> STOPPED_BUDGET   next safe reservation would exceed limit
  RUNNING --> FAILED           unexpected processing error
  BLOCKED / STOPPED_BUDGET / FAILED --> QUEUED --> RUNNING

The run does not become COMPLETED before Knowledge candidate analysis and its
spend/checkpoint data are saved.


I. INGESTION AND ZIP SCENARIOS
==============================

Expected input:

  weekly-zips/
    +-- 780123456.zip
    +-- 780123457.zip
    +-- ...

For each ZIP:

  inspect archive
      |
      +-- locate the primary PDF matching the ZIP/session ID
      +-- discover historical PDFs bundled with the primary session
      +-- extract text from the primary PDF
      +-- parse customer/agent messages and metadata
      +-- connect co-occurring sessions into an anonymous thread

Important input scenarios:

  Folder missing ----------------------> reject before run processing
  Folder contains zero ZIPs -----------> reject run creation
  Same folder has active/resumable run -> 409, do not create competitor
  ZIP has no matching primary PDF -----> extraction failure, auditable result
  Media-only chat ----------------------> not_scorable, no paid judgment
  Photo/document-only chat ------------> excluded by text eligibility rule
  Valid short bilingual text ----------> eligible; keep original wording
  Mixed Arabic/English and typos ------> retain text for multilingual model
  Historical PDFs present -------------> thread context only, no double count


J. JUDGMENT ENGINE
==================

Production evaluator:

  company-supervisor-v1

Inputs:

  +-- normalized customer and agent roles
  +-- original sender identifiers where useful
  +-- deterministic metrics
  +-- retrieved active company rules
  +-- approved supervisor precedents
  +-- prior context available in the session/thread

Decision contract:

  +----------------------+----------------------------------------------+
  | Status               | Meaning                                      |
  +----------------------+----------------------------------------------+
  | scored               | compliant or non_compliant company verdict   |
  | needs_clarification  | a real company rule/answer is missing         |
  | not_scorable         | unsupported, media-only, or insufficient text |
  | queued_for_rescore   | supervisor answer requires re-evaluation      |
  +----------------------+----------------------------------------------+

Non-compliant proof triangle:

             approved applicable rule
                      /\
                     /  \
                    /    \
         customer context ---- employee violation

If any corner is missing, the engine must not record a supported violation.

M. MANUAL EVIDENCE REVIEW
=========================

Evidence Lab case:

  +--------------------------------------------------------------+
  | Case category and model confidence                           |
  | Decision reason                                              |
  | Customer evidence                                            |
  | Agent evidence                                               |
  | Approved rule/reference used                                 |
  | Agent identity                                               |
  +--------------------------------------------------------------+

Supervisor confirms existing verdict:

  inspect evidence
       |
       +--> choose same verdict
       +--> write manager reason
       +--> save audit review
       +--> move case from pending to reviewed
       +--> DO NOT create a duplicate Knowledge rule

Supervisor corrects verdict:

  inspect evidence
       |
       +--> choose different verdict
       +--> write manager reason
       +--> write reusable company rule
       +--> backend derives corrected decision from stored score
       +--> update evaluation
       +--> create or update exactly one manager-review rule
       +--> preserve original result and review history

The backend ignores a client-supplied claim that a changed verdict was merely
"confirmed". It compares the manager verdict with the stored score itself.


N. NEW KNOWLEDGE AGENT
======================

Trigger:

  completed chat evaluation
        |
        +--> missing company rule patterns
        |
        v
  grouped knowledge_candidates
        |
        v
  local shortlist of nearest active rules
        |
        +-- normalized token overlap
        +-- Jaccard similarity
        +-- sequence similarity
        |
        v
  writer-model analysis with candidate + nearest rules
        |
        v
  persisted proposal, kind, reason, similarity, comparisons, conflict notes

Candidate kinds:

  NEW
    No equivalent active rule was found. Supervisor may approve a new rule.

  DUPLICATE
    Existing rule already expresses the required behavior. Supervisor confirms
    duplicate; the candidate closes and active Knowledge count does not grow.

  UPDATE
    Existing rule is related but should be refined. Supervisor may update the
    linked rule; no second rule is created.

  CONFLICT
    Proposal contradicts or overlaps an existing rule incompatibly. UI shows
    both rules and conflict notes before the supervisor decides.

  INSUFFICIENT
    Evidence does not justify a reusable company rule. Candidate remains
    inactive and should usually be rejected or await better evidence.

  UNREVIEWED / FAILED
    AI analysis has not completed or failed validation. Supervisor can retry
    analysis or perform a manual decision.

P. PAUSE, STOP, RESUME, AND CHECKPOINTS
=======================================

Checkpoint content includes:

  +-- evaluation version
  +-- private run settings snapshot
  +-- completed session IDs
  +-- last processed session ID
  +-- Knowledge agent statistics

Safe stop sequence:

  Admin               Flask/DB               Worker
    | POST stop           |                      |
    |-------------------->| set blocked request  |
    |<-- checkpoint_safe  |                      |
    |                     |<-- completes current safe boundary
    |                     |    no partial chat result

Resume sequence:

  Admin -> POST resume -> status QUEUED -> launch worker
                                      |
                                      +--> read checkpoint
                                      +--> subtract completed session IDs
                                      +--> process remaining/rescore IDs only

Invalid transitions:

  stop completed run without rescore work ----> 409
  resume completed run without rescore work --> 409
  resume already running run -----------------> 409
  unknown run --------------------------------> 404


Q. QUALITY KNOWLEDGE GOVERNANCE
===============================

No automatic activation path exists:

  AI proposal --------X--------> active production rule
                      |
                      v
              supervisor review required

Allowed candidate resolutions:

  approve + new
      -> require non-empty rule text
      -> reject if agent classified it as duplicate
      -> insert one active company-rule

  approve + update
      -> require linked existing rule
      -> update that item in place
      -> do not increase active rule count

  reject + duplicate
      -> document duplicate resolution
      -> create no rule

  reject + reject
      -> retain audit trail
      -> create no rule

Second mutation of a reviewed candidate is rejected.

T. TRANSACTION AND CONSISTENCY RULES
====================================

  - SQLite foreign keys are enabled.
  - WAL mode supports UI reads while the worker writes.
  - A busy timeout reduces transient write contention.
  - Repository mutations use explicit transactions.
  - Evaluation and spend are persisted with checkpoint progress.
  - Confirmation does not duplicate Knowledge.
  - Candidate update modifies one linked rule in place.
  - Candidate status prevents double review.
  - Active/inactive flags preserve history instead of destructive deletion.
  - Manual review history preserves previous supervisor decisions.

Startup migrations add missing candidate-analysis columns safely and repair
the historical confirmed-review duplicate pattern without deleting its audit.

W. WORKER CONCURRENCY AND COST SAFETY
=====================================

  one run worker
       |
       +--> inspect/extract sequential source sessions
       |
       +--> bounded AI worker pool
               |
               +--> reserve estimated cost before each request
               +--> evaluate independent eligible conversations
               +--> persist completed futures
               +--> update checkpoint after every safe completion

Budget rule:

  current actual spend
        + reserved maximum for pending work
        + next request maximum
        <= stop threshold

If false, the next request is refused before external spend occurs.
